Правила формирования тест-кейсов для импорта в PPTM (pptm-core, POST /app/testing/api/v1/test-issues, файлы test-cases-*.json): 1) Один шаг = бэк + фронт: `action` — бэкенд-запрос (сервис/метод/топик, заголовки, тело, внутренняя цепочка сервисов) + название экрана из «Экраны.md»; `expectedResult` — HTTP-статус, тело ответа, проверка БД + картинка экрана (base64 `<img>` из o:\Obsidian\img), соответствующая бэкенд-ответу. 2) Литеральный `\n` (два символа: backslash+n) в тексте шагов запрещён (в PPTM виден как два символа "\n") — использовать `<br>`; в f-строках генераторов не писать `\\n`. РЕАЛЬНЫЕ переводы строк (0x0a) ВНУТРИ `<pre><code>` ОБЯЗАТЕЛЬНЫ для форматирования JSON (indent=4) — они рендерятся как переносы в кодовом блоке; вырезать их (`replace('\n','')`) можно ТОЛЬКО вне `<pre>`, иначе JSON сжимается в одну строку (поймано на magnit-кейсах RPUP-1834). 3) Каждый кейс должен быть меньше ~256 КБ (иначе HTTP 500 от sfera-vtb-audit-adapter: 413 Payload Too Large): картинки сжимать до 480px / JPEG quality 45, дублирующие «пустые» экраны в одном кейсе не дублировать; после генерации проверять max-размер кейса по JSON. 4) HTTP 401 при импорте — проблема токена на стороне импортера, не данных: переимпортировать со свежим токеном. 5) preConditions/steps — массив объектов {action, expectedResult}, строки в массиве вызывают HTTP 500. 6) В описаниях (description) и шагах тест-кейсов не указывать ссылки на файлы-источники (напр. «(Экраны.md)») — в PPTM эта информация не несёт пользы; номера экранов (напр. «Экраны — 4.2.1») указывать можно. 7) Формат предусловий (preConditions) и шагов (steps) в PPTM: служебные метки «Шаг (Винительный падеж):» и «Ожидаемый результат (Именительный падеж):» в тексте НЕ писать. `action` в предусловиях — «N. <действие, ВИНительный падеж>» (номер ОБЫЧНЫМ шрифтом; шаг предусловия — ВСЕГДА действие-инфинитив: «Подключить тестового партнера», «Создать заявку», «Симулировать сбой» — НЕ состояние; состояние в Именительном падеже пишется в expectedResult: «Тестовый партнер подключен», «Заявка создана»); в шагах — «<b>N.</b> <b><заголовок шага, imperative></b>» (номер шага И заголовок шага ЖИРНЫМ — весь заголовок в секции «Шаги» должен рендериться жирным) + бэк-часть (вызов/заголовки/тело/внутренняя цепочка) + название экрана. ВАЖНО: теги `<b>…</b>` должны быть СБАЛАНСИРОВАНЫ (столько открывающих, сколько закрывающих) — при замене `N. <b>заголовок</b>` на `<b>N.</b> …` легко потерять открывающий `<b>` заголовка, и заголовок рендерится обычным шрифтом (поймано на magnit-кейсах: `<b>1.</b> Заголовок</b>`); после трансформации проверять баланс `<b>`/`</b>` и `<code>`/`</code>` в каждом поле. `expectedResult` — в предусловиях состояние после подготовки (именительный падеж), в шагах **жирное** (<b>…</b>) краткое резюме результата (1-2 предложения, именительный падеж) + HTTP-статус, тело ответа, проверка БД + картинка экрана. Фразы «Подготовить условие тестирования» и «Условие выполнено, окружение готово» не использовать.
